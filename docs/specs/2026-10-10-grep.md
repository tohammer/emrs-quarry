# Interactive grep

Status: implemented
Date: 2026-10-10

## Purpose

An interactive grep session for Emacs, in the manner of rg.el: ask for a
pattern, a file type and a directory, show the matches in a buffer, and
refine the search from there. It is faster to use than rg.el because the
search runs in the module and results arrive as structured values
(ADR 0011, ADR 0012). The search itself is a list of filters on lines and
paths that is shown in the buffer and can be changed there; the pattern
asked for at the start is the first of them. Results can be edited and
written back with wgrep (ADR 0013).

Success: a search in a tree of 20,000 files shows its results without a
noticeable wait; a path or line can be excluded with two keys and the
result updates; removing a filter is one key on its line; an edit made in
the result buffer reaches the file after the wgrep commit.

## Scope

In:

- A second emrs service, `grep`, in the quarry module, with its own
  directory walk that follows the walker rules of the index.
- `lisp/quarry-grep.el`: the commands, the result mode, filters, history.
- Filters on paths and on lines, each including or excluding, as
  literal or regexp.
- wgrep integration.
- A shared file `lisp/quarry-core.el` for finding, loading and building
  the module.

Out (candidates for later specs; evaluation section 6):

- Editing filters in the buffer as you type; context lines; filters on
  file content ("files that also contain X"); multi-line matches.
- A consult front end; replace with preview; saved and named searches.
- Use of the file index or the watcher (ADR 0010).
- Remote directories. The commands signal a `user-error` that names rg.el
  as the tool for them.
- PCRE2, compressed files, `~/.ripgreprc` (ADR 0011).

## Design

### Components

| Component | Responsibility |
|---|---|
| `src/walk.rs` (changed) | Also builds a walker for a caller that brings its own options: ignore files on or off, an extra entry predicate, file types. The index's walk behaves as before |
| `src/grep/filter.rs` | Path and line filters: compile, match, decide whether a directory can be skipped |
| `src/grep/search.rs` | One search: walk, search each file, collect lines and match positions, cap, order |
| `src/grep/service.rs` | `GrepService`, emrs service `"grep"`: requests, the search task, the type list |
| `lisp/quarry-core.el` | Module file lookup, loading, the offer to build; the options `quarry-include-hidden` and `quarry-ignores`. Moved out of `quarry.el`, which requires it |
| `lisp/quarry-grep.el` | Commands, prompts, `quarry-grep-mode`, rendering, filters, history, wgrep glue. Requires `quarry-core`, not `quarry` |

`quarry-grep.el` works with `quarry-mode` off and never starts an index
instance. New crates: `grep-regex`, `grep-searcher`, `grep-matcher`.

### The service

One instance serves all result buffers; `quarry-grep.el` starts it on
first use and starts a new one after a failure. It keeps no state between
requests.

`(:types)` replies with the list of file types, each a name and its
globs, from the defaults of the `ignore` crate (the list `rg --type-list`
prints).

`(:search …)` replies with a stream. Fields:

| Field | Meaning |
|---|---|
| `dir` | Absolute directory to search |
| `filters` | The enabled filters, in the buffer's order (below). At least one must be an include line filter |
| `case` | Case rule for line filters: `smart`, `sensitive` or `insensitive` |
| `file-type`, `globs` | A type name from `(:types)`, or globs given by the user; neither means all files |
| `no-ignore` | Do not apply `.gitignore`, `.ignore` and git exclude files |
| `hidden` | Search hidden files |
| `ignores` | Extra gitignore lines, relative to `dir` |
| `max-lines`, `max-columns` | The caps described below |
| `sort-budget-ms` | How long results are collected to be sent sorted (below); 150 unless given |

Version control directories (`.git`, `.hg`, `.svn`, `.jj`) are never
searched, also with `no-ignore`. Symbolic links are not searched, to
files or to directories, so a file appears once, under its real path.
Files with a NUL byte are skipped as binary. A byte order mark selects
the encoding; otherwise files are read as UTF-8. In files with `\r\n`
line ends the `\r` is not part of the line: it is not shown, and `$`
matches before it.

Stream items are of two kinds:

- A **file** item: the path relative to `dir`, the positions in that
  path matched by include path filters, the file's modification time,
  and its matching lines. Each line has its number, its text without the
  line terminator, the match positions as character offsets into that
  text, and a flag `inexact`. Each match position says whether it comes
  from the primary filter or from another include line filter; where the
  two overlap, the primary one is reported.
- One **summary** item, last: files searched, files with matches, lines,
  whether the line cap was reached, whether the files arrived sorted, the
  elapsed time, and the number of files that could not be read.

`inexact` is set when the text is not exactly the file's line: it was cut
at `max-columns` characters, or it held bytes that are not valid UTF-8.

The exact Lisp shapes are documented in the module docs of
`src/grep/service.rs`, as `src/service.rs` does for the index.

**Cap.** When `max-lines` lines have been collected the search stops and
the summary says so.

**Order.** The search collects results for 150 ms. If it finishes within
that time, the file items are sent sorted by path. Otherwise the items
collected so far are sent sorted, and the rest follow as they are found;
the summary then reports the result as not sorted.

**Cancellation.** The search task checks the stream's token between files
and stops. Emacs cancels a running search when a new one starts in the
same buffer, when the buffer is killed, and on `C-c C-k`.

### Filters

A search is a directory, a file type and a list of filters. A filter has
a target (`line` or `path`), a direction (include or exclude), a pattern,
a syntax (literal or regexp) and is enabled or not. Disabled filters stay
in the list and are not sent to the service.

The pattern the commands ask for becomes the first filter, an include
line filter. It is an ordinary filter: it can be edited, switched between
literal and regexp, and removed when another include line filter exists.

- A **line** filter is matched against the text of a line. Regexps are
  Rust regexps. The search's case rule applies to every line filter,
  literal or regexp: `smart` means insensitive unless that filter's
  pattern has an uppercase letter.
- A **path** filter is matched against `/` followed by the path relative
  to the search directory, with `/` as separator. So `/test/` matches
  `test/a.c` and `src/test/a.c`, and `.rs` matches by extension. Path
  filters always use smart case.
- A file or line is kept when it matches **every** enabled include filter
  of its target and **no** enabled exclude filter. Each added filter can
  only narrow the result.
- The **primary** filter is the first enabled include line filter. The
  engine scans the files for it; the other line filters are tested on the
  lines it finds. Since all include filters must match, the choice of the
  primary filter does not change which lines are found, only how they are
  highlighted and where point lands when a result is visited.
- A search needs a primary filter. Removing, switching off or flipping
  the only enabled include line filter is refused with a `user-error`.
- A literal exclude path filter is also tested against each directory, as
  its path with a trailing `/`. A directory that matches is not entered.
  Regexp exclude filters are tested against files only: a regexp can
  match a directory's path without matching the files below it.
- A filter equal to an existing one (target, direction, pattern, syntax)
  is not added again; if the existing one is switched off, it is switched
  on instead.
- The text anchors `\A` and `\z`, and switching multi-line mode off, are
  not supported in line filters; `^` and `$` are.
- Path filters are applied before a file is opened.

Every change to the filters runs the search again.

**Highlighting.** Matches of the primary filter use the face
`quarry-grep-match`. Matches of the other include line filters use
`quarry-grep-match-secondary` when `quarry-grep-highlight-include-filters`
is non-nil (the default). The parts of a file heading's path matched by
include path filters use `quarry-grep-path-match` when
`quarry-grep-highlight-path-filters` is non-nil (the default). Exclude
filters have nothing to highlight.

### Commands

| Command | Asks for | Searches |
|---|---|---|
| `quarry-grep` | regexp, file type, directory | the directory |
| `quarry-grep-literal` | string, file type, directory | the directory |
| `quarry-grep-project` | regexp, file type | the project root (`project-current`), or `default-directory` outside a project |
| `quarry-grep-dwim` | nothing | the project root for the symbol at point as a literal, in files of the current buffer's type |

Each command starts a search whose only filter is an include line filter
with the pattern, as regexp or literal.

The pattern prompt offers the active region or the symbol at point as
default. The file type prompt completes over the names from `(:types)`
plus `everything`; its default is the type whose globs match the current
buffer's file name, else `everything`. Input that is not a type name is
taken as one or more globs separated by spaces. Globs match file names,
not paths; a glob that contains `/` is refused. An empty pattern is a
`user-error`.

Options: `quarry-grep-case` (default `smart`), `quarry-grep-max-lines`
(default 50000), `quarry-grep-max-columns` (default 500),
`quarry-grep-buffer-name` (default `*quarry-grep*`),
`quarry-grep-highlight-include-filters` and
`quarry-grep-highlight-path-filters` (both default t). Hidden files and
extra ignore lines start from `quarry-include-hidden` and
`quarry-ignores`.

### The result buffer

One buffer, reused by each new search. Its `default-directory` is the
search directory.

```text
 files: rust   dir: ~/src/emacs-quarry/   case: smart   ign: on   hidden: on   hits: 7 in 2 files
 ------------------------------------------------------------------------ (header line)
 + line/re  fn \w+_walk
 + line     pub                                    (off)
 - line/re  ^\s*//
 - path     /tests/

 File: src/walk.rs (5)
   169 pub fn walk(
   182 pub fn walk_dirs(
   ...

 File: src/grep/search.rs (2)
    41 pub fn walk_and_search(
   ...

 Search finished: 7 lines in 2 files, 61 ms
```

- The **header line** shows the file type, the directory, the toggles
  and the counts. Its parts can be clicked and run the same commands as
  the keys below.
- The **filter block** has one line per filter, in the order they were
  added; the first line is the pattern the command asked for. A disabled
  filter is shown dimmed with `(off)`; a regexp filter is marked
  `line/re` or `path/re`.
- A **file block** has a heading with the relative path and the number of
  lines, then one line per match: the line number, right-aligned, and the
  text with the matches highlighted (section "Filters").
- The **status line** at the end says `Searching…` while the stream runs,
  then the summary; it names a reached cap ("stopped at 50000 lines,
  narrow the search"), unreadable files, a cancellation or an error.

File items are appended in the order they arrive. Point and the window
start stay where they are while results come in.

A search started from the result buffer (rerun, a toggle, a filter
change, history) returns point to the result it was on: the same line if
it is found again, else the file's heading; if the file is no longer in
the result, the next heading in path order. Point on a filter line stays
at that position in the filter block. The four commands start at the top.

Keys. Evil is not supported specially; the map follows rg.el where rg.el
has the command.

| Key | Action |
|---|---|
| `RET`, `mouse-1`, `mouse-2` | On a match line or its number: visit the file at that line, at the column of the first match of the primary filter. On a file heading: visit the file. On a filter line: edit the pattern in the minibuffer |
| `n`, `p` | Next or previous match, shown in another window without selecting it |
| `}`, `{`, `M-N`, `M-P` | Next or previous file |
| `TAB`, `S-TAB` | Fold or unfold the file block at point; all blocks |
| `g` | Search again |
| `r`, `t` | Edit the primary filter, as regexp or as literal |
| `d`, `f` | Change the directory; the file type |
| `c`, `i`, `H` | Cycle case (smart, sensitive, insensitive); toggle ignore files, hidden files |
| `- p`, `+ p` | Add a path filter, excluding or including |
| `- l`, `+ l` | Add a line filter, excluding or including |
| `- P`, `+ P`, `- L`, `+ L` | The same, with the pattern as a regexp |
| `- f` | Exclude the file at point, with a regexp filter that matches exactly that path |
| `- d`, `+ d` | Exclude, or search only, the directory of the file at point; the prompt holds the directory and can be shortened to a parent |
| `k`, `x`, `!`, `%` | On a filter line: remove it; switch it on or off; flip include and exclude; switch literal and regexp |
| `K` | Remove all filters except the primary one |
| `C-c <`, `C-c >` | Go back or forward in the buffer's search history |
| `C-c C-k` | Cancel the running search |
| `e` | Edit the results with wgrep |
| `q` | Quit the window |

`next-error` and `previous-error` work from other buffers. Every search
that differs from the previous one, filters included, is an entry in the
buffer's history; going back or forward runs that search again.

### wgrep

`e` enters wgrep's edit mode; `C-c C-c` and `C-c C-k` there are wgrep's
commit and abort. quarry sets `wgrep-header&footer-parser` and
`wgrep-results-parser` to functions that read its own text properties:
the filter block is the header, the status line the footer, file
headings are ignored, and each match line gets its file and line number.
Lines flagged `inexact` are read-only.

`e` is refused while a search runs, when there are no results and when
wgrep is not installed. Entering edit mode unfolds all file blocks. After
a commit that changed lines, the status line says that the results were
edited and that `g` searches again.
Before entering, quarry compares each result file's modification time
with the one from the search and checks whether a buffer visiting it is
modified. If any differ it asks whether to search again first; the
answer no enters edit mode on the results as they are.

## Error handling

| Situation | Behaviour |
|---|---|
| Invalid regexp in a filter | The call fails before anything is searched; the status line shows the engine's message and the filter's pattern. The filters stay as they are, so `RET` on the filter can correct it |
| Removing, switching off or flipping the only enabled include line filter | `user-error`; nothing changes |
| Directory missing, not a directory, or remote | `user-error` at the prompt; a directory that vanished before a rerun is reported in the status line |
| File unreadable or removed during the search | Skipped and counted; the status line shows the count |
| Line cap reached | The search stops; the status line says so |
| The instance fails (panic) | The running search ends with the error in the status line; the next search starts a new instance |
| Module missing | The shared offer to build it, as for the file finder |
| wgrep missing | `e` signals a `user-error` that names the package |
| Result buffer killed during a search | The search is cancelled |

- **Rust, filters:** literal and regexp, the case rule for line filters,
  smart case for path filters, the leading `/` rule, include and exclude
  combinations, skipping of directories, the choice of the primary
  filter, a request without an include line filter.
- **Rust, service** (through `emrs::testing::Host` on temporary trees):
  matches with line numbers; match positions as character offsets on
  lines with non-ASCII text, marked as primary or secondary, with
  overlaps; matched positions in paths; literal and case modes; file type
  and globs; ignore files on and off; hidden files; version control
  directories; binary files; each filter kind; `inexact` for long lines
  and invalid UTF-8; the line cap; sorted order for a quick search;
  cancellation; invalid regexps; unreadable files in the summary; the
  type list.
- **Rust, walker:** the index's walk tests still pass unchanged.
- **ERT** (generated trees, the debug module, as the existing suite):
  each command with simulated prompts; the buffer's content addressed by
  text property; header and status line; visiting from a match line and
  a heading; `next-error`; each toggle and change command; filter add,
  remove, switch off, flip, syntax switch, edit, remove all; the refusal
  to lose the primary filter; the three highlight faces and the two
  options that switch them off; filters from the result at point; history back and forward; cancel; the error rows
  above; `quarry-grep.el` loads and searches with `quarry-mode` off and
  without `quarry.el` loaded.
- **ERT with wgrep** (skipped when wgrep is not on
  `QUARRY_TEST_LOAD_PATH`): an edited line reaches the file after
  commit; abort leaves it; headings, filter lines and `inexact` lines
  cannot be edited; the stale check asks.
- **Manual:** mouse clicks on line numbers and header parts; folding;
  appearance in the author's theme; a search for a common word in a tree
  of about 20,000 files, compared by feel with `M-x rg` for the same
  query; a search that reaches the cap.
