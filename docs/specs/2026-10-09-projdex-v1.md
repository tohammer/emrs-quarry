# projdex version 1: live project file index with fuzzy finder

Status: approved
Date: 2026-10-09

## Purpose

`project-find-file` is slow on large repositories: it lists every file
(`git ls-files` or `find`) on each call and then filters thousands of
candidates in Lisp. projdex keeps a live index of each project's files in a
Rust service built on emrs, kept current by a file watcher, and answers
each keystroke of a `completing-read` prompt with nucleo-ranked matches.

Users are Emacs users who open files in large projects many times a day.
projdex is also the first real module built on emrs, so it must exercise
the emrs features a real module needs: start arguments, long-lived state,
several instances, request/reply, streams with backpressure, self-messages,
events, cancellation, logging, `on-exit`, and `emrs-call-sync` latency.

Success:

- `projdex-find-file` finds the same files `project-find-file` would offer
  (rules under Design, "What is indexed"), ranked usefully.
- Creating, deleting and renaming files shows up in the next query without
  user action.
- End-to-end latency per completion-table call, with a limit of 100
  results, measured by the benchmark script (Testing) on the developer's
  machine: p99 at most 50 ms on a generated tree of 100,000 files. On
  1,000,000 files (the size of an AOSP checkout), p99 at most 150 ms is a
  goal, not a requirement of version 1: the developer's 4-core laptop
  measured 177 ms on 2026-10-09 with exact ranking, and the user chose to
  keep exact ranking over a faster approximate first pass (backlog,
  "Faster scoring for very large indexes").
- The Rust and ERT suites cover everything listed under Testing.

## Scope

In:

- Rust service `projdex`: walk, index, fuzzy matching with match positions,
  file watcher, rescan, status, a stream of all files.
- `projdex.el`: one instance per project root, started lazily; the
  `projdex-find-file` command with a `completing-read` table and the
  pass-through completion style `projdex` (ADR 0001, ADR 0002); match
  highlighting; `projdex-mode`, which remaps `project-find-file` and
  optionally serves `project-files`; commands to rescan, stop and show
  status.
- Rust tests, ERT tests, a benchmark script.

Out (deliberately):

- consult async source (backlog, ADR 0001).
- Remote projects (TRAMP): projdex falls back to `project-find-file`.
- Ignored files (`project-find-file` with a prefix argument): falls back.
- Recently-used ordering, frecency, or any persistence of the index.
- Limits on the number of instances or idle shutdown of instances.
- Non-UTF-8 file names: skipped and counted (Error handling).
- Windows: not tested in version 1. The code must build there, but
  behaviour is not verified.
- CI and distribution (backlog).

## Design

### Overview

```text
 Emacs thread                               runtime threads (emrs pool)
 projdex.el                                 projdex service, one per root
   projdex-find-file                          index: paths + matcher
     completing-read ── table ── emrs-call-sync (:query) ─► handle
                                                            ▲  ▲
   project-files :around ── emrs-call-stream (:files) ─────┘  │ self-messages
   on-event ◄── (:indexed) (:changed) (:watch-failed) ◄─┐     │ (walk batches,
                                                         └─ walk task, watcher
```

The service owns the index. Mutations (walk batches, file-system changes)
reach it as self-messages through `ctx.address()`, so all index access
happens inside `handle`, one message at a time, and needs no locking.

### Rust crate layout

| File | Responsibility |
|---|---|
| `src/lib.rs` | `emrs::module!("projdex", [Projdex])` and module docs |
| `src/service.rs` | `Projdex`: `Args`, `Request`, `Event`, `start`, `handle`, `stop`; generations; pending `:files` and `:rescan` replies |
| `src/index.rs` | The path set: add, remove, remove by directory prefix, iterate; stores paths for nucleo |
| `src/matcher.rs` | Query text → ranked paths with match positions |
| `src/walk.rs` | Walker configuration and the walk task, sending batches |
| `src/watch.rs` | Watcher set-up, translation of file-system events into index changes, rescan triggers |

Dependencies: `emrs` (pinned git commit), `serde`, `ignore`,
`nucleo-matcher` (pinned upstream git commit, ADR 0003), `notify`, `notify-debouncer-full`; dev: `tempfile`. The
minimum Rust version rises to 1.88, the minimum of current `ignore` and
`notify` releases.

### What is indexed

- Regular files below the root, and symbolic links to files. Directories
  are not entries. Symbolic links are not followed.
- `.gitignore`, `.ignore`, `.git/info/exclude` and the user's global git
  excludes apply, also outside a git repository (`require_git(false)`).
- Hidden files are included unless `include_hidden` is false.
- The directories `.git`, `.hg`, `.svn` and `.jj` are never walked, at any
  depth.
- `ignores` from the start arguments are extra gitignore-syntax patterns
  relative to the root.
- Paths are stored relative to the root, with `/` as separator and no
  leading `./`.
- The walk uses `ignore`'s parallel walker (`WalkParallel`) with one
  thread per available core, so a first walk of an AOSP-sized tree takes
  seconds. Batches of at most 1,000 paths are sent to the service; their
  order is not significant.

Differences from `project-files` are documented in the README: projdex
includes untracked files that are not ignored, regardless of
`project-vc-include-untracked`, and does not honour `project-vc-ignores`
(use `projdex-ignores`).

### Start arguments

```rust
struct Args {
    root: String,          // absolute path of an existing directory
    include_hidden: bool,
    ignores: Vec<String>,  // gitignore-syntax lines
}
```

Lisp: `(:root "/home/u/src/x/" :include-hidden t :ignores ("*.min.js"))`.

`start` validates the root, sets up the watcher (a failure there does not
fail `start`; see Error handling), and spawns the first walk. It returns
without waiting for the walk.

### Requests and replies

`Request` variants Elisp may send, and their replies:

| Request (Lisp) | Reply |
|---|---|
| `(:query :text S :limit N :positions BOOL)` | `(:paths (P ...) :positions (POS ...) :total M :indexing BOOL)` |
| `(:files)` | Stream of strings (relative paths), capacity 4096 |
| `(:rescan)` | Number of files, when the walk it started has finished |
| `(:status)` | `(:root R :files N :indexing BOOL :watching BOOL :walks K :skipped S)` |

- `:query`: matches `text` against the index (Matching below) and returns
  at most `limit` paths, best first. `limit` is clamped to 1..=10000.
  `:positions` is a list parallel to `:paths`; each element is the sorted
  list of character indices that matched, or `:positions` is nil when not
  requested. `:total` is the number of matching paths before the limit.
  `:indexing` is true while a walk is running; the answer then reflects the
  paths seen so far.
- `(:files)`: if a walk is running, the reply waits until it finishes; then
  the handler streams a snapshot of the index (taken in `handle`) from a
  spawned task, so the instance keeps answering queries while the stream
  drains. The task stops when the stream's token is cancelled.
- `(:rescan)`: starts a new walk (new generation, see below), cancelling a
  running one, and answers once a walk completes. All pending `(:rescan)`
  and `(:files)` replies are answered at the `WalkDone` of the newest
  generation; none is answered from a walk that was superseded.
- `:walks` counts finished walks; `:skipped` counts paths skipped in the
  last walk (non-UTF-8 names, unreadable directories).

Internal variants, marked `#[serde(skip_deserializing)]` and sent only by
the service's own tasks:

- `WalkBatch { generation, paths }` and `WalkDone { generation, skipped,
  millis }` from the walk task.
- `FsChanges(Vec<Change>)` from the watcher, and `WatchFailed(String)`.

**Generations.** Each walk has a generation number. A new walk replaces the
index: batches of the current generation are added to a fresh index that
becomes current at `WalkDone`; until then, queries use the previous index
(or the partial fresh one during the first walk, when there is no previous
one). Batches and `WalkDone` of an older generation are discarded, and
starting a new walk cancels the old walk's token. File-system changes that
arrive during a walk are applied to the current index and recorded; at
`WalkDone` they are replayed on the fresh index, so no change is lost.

### Events

| Event (Lisp) | When |
|---|---|
| `(:indexed :files N :millis T)` | A walk finished and its index became current |
| `(:changed :added A :removed R)` | A batch of file-system changes changed the index (`A + R > 0`) |
| `(:watch-failed :message S)` | The watcher could not be set up or stopped working |

### Matching

- `nucleo_matcher::Matcher` with `Config::DEFAULT.match_paths()`.
  Matchers are kept by the instance and reused across queries.
- The query is parsed with `Pattern::parse(text, CaseMatching::Smart,
  Normalization::Smart)`: space-separated atoms in any order, `^prefix`,
  `suffix$`, `!negation`, `'exact`.
- Order: score descending, then path length ascending, then path
  ascending. An empty query matches every path in that tie-break order.
- Match positions come from nucleo's `indices` output for the returned
  paths only, sorted and deduplicated.
- **Parallel scoring.** When the set to score has more than 10,000 paths,
  it is split into one chunk per available core (`std::thread::available_parallelism`),
  scored on scoped threads with one matcher each, and the per-chunk top
  `limit` results are merged. Below that size, scoring is single-threaded.
  The result is identical to single-threaded scoring.
- **Incremental narrowing.** The instance remembers the last query's text,
  the index version it ran against, and the full set of matching paths
  (not only the top `limit`). The next query scores only that set when all
  of these hold: the index has not changed since (any add or remove bumps
  the version; versions are unique across index instances); the new text
  starts with the old text; the old text does not end with `\` or `$`;
  neither the old text's last atom nor the appended part contains `!` or
  `$`; and not both of them contain non-ASCII characters (typing a
  non-ASCII character switches nucleo's smart normalization off for that
  atom, which can widen the match set). The last atom is split the way
  nucleo splits: at any whitespace character not preceded by `\`.
  Otherwise the whole index is scored. The result is identical to scoring
  the whole index.

### Watching

- The watcher covers exactly the directories the walk visits: ignored
  directories and the VCS directories above are not watched. Directories
  that appear later are watched when they are added. (On Linux this means
  one non-recursive inotify watch per indexed directory; on macOS the
  implementation may watch the root recursively and filter, since FSEvents
  is not per-directory.)
- Events are debounced with `notify-debouncer-full` with a 100 ms window.
  Its file-id rename pairing is not used (on macOS and Windows it scans the
  whole tree, ignored directories included); every affected path is
  instead compared with the disk when the event is handled, which makes
  paired and unpaired rename halves behave the same.
- Translation into index changes:
  - file created or renamed into the tree, not ignored: add;
  - file removed or renamed out: remove;
  - directory created or renamed into the tree: walk it with the same
    rules (inside the watcher thread), add its files, watch its
    directories;
  - directory removed or renamed out: remove every path under it and drop
    its watches;
  - content modifications and metadata changes: ignored.
- A change to an ignore file (`.gitignore`, `.ignore`, `.git/info/exclude`)
  anywhere in the tree starts a full rescan instead of an incremental
  change, because it can change which files are indexed.
- When the backend reports lost events (inotify queue overflow, notify's
  rescan flag), the service starts a full rescan.

### Elisp

Defcustoms (group `projdex`):

| Option | Default | Meaning |
|---|---|---|
| `projdex-include-hidden` | `t` | Index hidden files |
| `projdex-ignores` | `nil` | Extra gitignore-syntax patterns |
| `projdex-limit` | `200` | Candidates per query |
| `projdex-highlight` | `t` | Highlight matched characters |
| `projdex-query-timeout` | `10.0` | Seconds before a query gives up; a safety net against a stuck instance, not a latency budget |
| `projdex-provide-project-files` | `nil` | With `projdex-mode`, serve `project-files` from the index |
| `projdex-files-timeout` | `10.0` | Seconds `project-files` waits before falling back |

Option changes apply to instances started afterwards; the README says to
run `projdex-stop` to restart a project's instance.

**Instances.** A hash table maps the root (`file-name-as-directory` of the
expanded `project-root`) to a record holding the emrs instance, the file
count, `indexing`, `watching`, and an epoch counter. `projdex--ensure ROOT`
returns the running instance or starts one with `emrs-start 'projdex
"projdex" ARGS :on-event ... :on-exit ...`. `on-event` updates the record;
`:indexed` and `:changed` increment the epoch; `:watch-failed` sets
`watching` to nil and logs a warning once. `on-exit` removes the record;
for status `failed` it shows a warning with the error message. The next
command on that project starts a new instance; there is no automatic
restart.

**Query core.** `projdex-query ROOT TEXT LIMIT &optional POSITIONS`
returns the reply plist via `emrs-call-sync` with `projdex-query-timeout`.
`projdex-query-async` does the same with `emrs-call` and a callback; it has
no caller in version 1 but is the entry point for the later consult
adapter, and is tested.

**Completion table.** `projdex--table ROOT` returns a function
`(STRING PRED ACTION)`:

- `metadata`: `(metadata (category . project-file) (display-sort-function
  . identity) (cycle-sort-function . identity))`.
- `t` (all completions): the paths of `projdex-query` for STRING, filtered
  by PRED if non-nil, highlighted when `projdex-highlight` is non-nil:
  copies of the paths with `completions-common-part` added at the match
  positions (`add-face-text-property`).
- `nil` (try completion): `t` if STRING is the only result and equal to it;
  otherwise STRING if there are results; nil if none.
- `lambda` (test completion): whether STRING is among the results for
  STRING.
- `(boundaries . _)`: nil (the whole input is the query).
- Results are cached per (STRING, epoch, limit), keeping only the most
  recent few entries, because completion UIs call the table several times
  per keystroke.

**Completion style.** `projdex` is added to `completion-styles-alist`. Its
all-completions function returns the table's `t` result with base size 0;
its try-completion function returns the table's `nil` result, as `(STRING
. POINT)` when it is a string. `projdex-find-file` let-binds
`completion-category-overrides` with `(project-file (styles projdex))` in
front (ADR 0002).

**`projdex-find-file`** `(&optional INCLUDE-ALL)`: takes the project like
`project-find-file` (`project-current t`). With INCLUDE-ALL, or when the
root is remote (`file-remote-p`), it calls `project-find-file` with the
same argument instead. Otherwise it reads a path with `completing-read`
(prompt `Find file in <project name>: `, require-match `confirm`, history
`projdex-file-history`) and visits `(expand-file-name PATH ROOT)` with
`find-file`. When the instance is not watching, it first sends `(:rescan)`
with `emrs-send`, so the index catches up while the user types.

**`projdex-mode`**: a global minor mode whose keymap remaps
`project-find-file` to `projdex-find-file`. With
`projdex-provide-project-files` non-nil, the `project-files` `:around`
method below is active.

**`project-files`.** A `cl-defmethod project-files :around (project
&optional dirs)` that applies only when `projdex-mode` and
`projdex-provide-project-files` are non-nil, DIRS is nil or the project
root alone, the root is local, and an instance for the root already exists.
It collects `(:files)` with `emrs-call-stream`, waiting in an
`accept-process-output` loop up to `projdex-files-timeout`, and returns
absolute file names. On timeout or error it cancels the call and returns
`(cl-call-next-method)`. A quit cancels the call and propagates. Otherwise
it returns `(cl-call-next-method)` directly.

**Commands.** `projdex-rescan` (current project; reports the file count
when done), `projdex-stop` (current project), `projdex-stop-all`,
`projdex-status` (shows the `:status` reply in the echo area).

## Error handling

| Situation | Behaviour |
|---|---|
| Root missing, not a directory or not absolute | `start` fails with a service error; `on-exit` gets `failed`; `projdex-find-file` signals a `user-error` with the message |
| Module not found on `load-path` | `emrs-start` signals; `projdex-find-file` turns it into a `user-error` saying where the module must be installed |
| Unreadable directory during a walk | Skipped, counted in `:skipped`, logged at `warn` once per walk with the count |
| Walk fails as a whole (invalid ignore file set-up, cancelled by stop) | The previous index stays current; error logged; no `:indexed` event; pending `(:rescan)` calls fail with the message; pending `(:files)` streams send the current index. A vanished root is not an error: the walk yields 0 files and counts skipped entries |
| Non-UTF-8 file name | Skipped, counted, logged as above |
| Watcher set-up fails (limit reached, unsupported file system) | Instance keeps running without watching; `:watch-failed` event; `projdex-find-file` sends `(:rescan)` before each prompt |
| Watcher fails later (backend error) | Same as above; existing watches are dropped |
| Lost file-system events | Full rescan |
| Query exceeds `projdex-query-timeout` | `emrs-call-sync` cancels the call; the table returns no candidates and shows a message once per prompt |
| User quits during a query | `emrs-call-sync` cancels the call; the quit propagates |
| Completion UI abandons a call (`while-no-input`) | Same as quit: the call is cancelled |
| Instance fails (panic) | `on-exit` shows a warning and removes the record; the next command starts a new instance |
| `project-files` stream fails, is cancelled by timeout, or the instance stops | Falls back to `cl-call-next-method` |
| Index changes while a `(:files)` stream drains | The stream delivers the snapshot taken when it started |

## Testing

**Rust (`cargo test`)**, with `tempfile` trees and `emrs::testing::Host`:

- `index`: add, remove, prefix removal, no duplicates.
- `matcher`: ranking order including tie-breaks, smart case, negation and
  anchors, positions are character indices (test with non-ASCII paths),
  limit and `total`, empty query.
- `walk`: results equal to a single-threaded reference walk,
  `.gitignore` at several levels, `.ignore`, `.git/info/exclude`,
  extra `ignores`, hidden on and off, VCS directories excluded, symlinks
  not followed, separators and relative form, non-UTF-8 names skipped and
  counted (Unix only).
- Service through `Host`: bad roots fail `start`; queries answer during
  and after the first walk (`indexing` flag); `:indexed` event; `(:files)`
  waits for a running walk and streams the whole index; a cancelled
  `(:files)` stream stops its task; `(:rescan)` answers after the new walk;
  stale generations are discarded; changes during a walk are kept.
- Watcher through `Host` with real file-system changes (waiting for
  events with a timeout): create, delete, rename of files and directories;
  files in ignored directories do not appear; editing `.gitignore` triggers
  a rescan and the result reflects the new rules; a directory created
  after start is watched.

**ERT (`tests/run-ert.sh`)**, on generated temporary trees:

- The table returns ranked paths; metadata; try/test completion; the
  `projdex` style keeps the order; highlighting applies the face at the
  right characters and is off when `projdex-highlight` is nil.
- `completing-read` driven with `execute-kbd-macro` or
  `minibuffer-with-setup-hook` opens the expected file.
- Cache invalidation: create a file, wait for `:changed`, the next query
  includes it.
- One instance per root; two roots give two instances; `projdex-stop`
  ends one; a failing start produces a `user-error` and no record.
- Remote root and INCLUDE-ALL fall back to `project-find-file` (with
  `project-find-file` stubbed).
- `projdex-mode` remaps the command and disabling it removes the remap.
- `project-files`: inactive by default; with the option it returns the
  same set as a directory listing applying the same rules; falls back on
  timeout (stubbed) and when no instance exists.
- `projdex-query-async` delivers to its callback.

**Benchmark (`bench/run-bench.sh`)**: generates trees of 100,000 and
1,000,000 files in nested directories with AOSP-like path lengths and
depths, each in a temporary git repository, then for each tree:

- measures the time to the first `:indexed` event and the module's
  resident memory after it;
- types a fixed sequence of queries (prefixes of several realistic
  queries, about 100 calls) through `completion-all-completions` with the
  `projdex` style and limit 100, timing each call; prints p50, p95, p99
  and max; exits non-zero if p99 exceeds 50 ms (100k) or 150 ms (1M; a
  failure there reports the goal as missed);
- runs the same queries against the baseline (`project-files` of the vc
  backend, then `completion-all-completions` with the `flex` style) and
  prints the same figures, without a threshold. On the 1M tree the
  baseline may be skipped with a flag if it takes too long.

The matcher also gets a Rust test that parallel scoring and incremental
narrowing return exactly what single-threaded full scoring returns, over a
generated set of paths and a list of query sequences, including ones that
must not narrow (`!`, `$`, deleted characters).

The benchmark is run manually; its result is recorded in the README.

**Manual checks**: `projdex-find-file` in the default completion UI, in
icomplete/fido, and in vertico if installed; highlighting visible; a file
created from a shell appears in the next prompt.
